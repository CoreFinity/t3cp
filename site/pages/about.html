About t3cp.

An independent record of how T3 Code performs. Every upstream nightly, measured the same way, in seven cells: 1, 50, 100, 150, 200 and 250 agents, plus a fresh install, one agent. The performance fork's releases sit on the same charts.

This project looks at T3 Code the way it is run in production: hundreds of agents, orchestrated across one or more machines, all through one server. At that load the server shows problems a single developer at a laptop never meets: a main thread close to saturation, reads waiting for a connection, memory that grows by the hour, queued runs that start late.

So every nightly is measured the same way, at one agent and at up to 250, and the numbers are published the day they are taken. The performance fork works on the server and sends its fixes upstream as pull requests; its releases are measured against their upstream base, built from source, on the same charts as the nightlies.

How it is measured.

Load
1, 50, 100, 150, 200 and 250 agents. At each level N: N agents, 3 people watching live, switching threads every 300 s, and status polling that grows with N; each agent waits 60 s between turns (5 s at 1 agent). Each agent is one streaming session on the server; 1 agent is one developer starting a new thread on the same large database. At the higher levels the server may saturate: those attempts are published and flagged with how many agents were served, and their latency is context only.
Run
60 s warm-up, 300 s measured, three attempts per level. The value is the median of the three.
